# Problem Statement 26155 — requirement-to-evidence map

Use this wording on slides. Each row says what exists, where to see it, and the
limit to state if asked.

| Requirement phrase | What the system does | Where | Limit to be upfront about |
|---|---|---|---|
| Collect data with Python libraries (Netmiko / NAPALM) | Dual ingest: online collection over SSH with Netmiko (default) or NAPALM, **and** offline file upload / drop-folder for air-gapped sites. Both feed the same ingest gate (MIME check, credential redaction, hashing, dedup). | `services/ingestion/app/collector.py`, `POST /api/collect`, upload-screen form | Off by default and restricted to `COLLECTOR_ALLOWED_CIDRS`; never used in air-gapped mode. Netmiko is the tested path; NAPALM has drivers for IOS/NX-OS/EOS/Junos only. Device commands per platform are a table to extend. Not yet tested against real devices. |
| Device identification incl. serial numbers and hardware details | Extracts hostname, vendor, OS, software version, hardware model and serial number; shows them in the audit header and the PDF's "Device Identification" table. | `services/parsing/app/device_identity.py`, `audit_report.html` | Only what the config text carries (Cisco `license udi` line, FortiOS `#config-version` header, `Serial Number:`/`Model:` lines, pasted `show` output). A plain running-config often has none, and the report then says "not found in configuration" rather than guessing. |
| NLP / pattern matching to find keywords the system is not trained on | Unrecognised blocks go to the Learning queue with the unfamiliar command words extracted, ranked (command position, frequency) and flagged when security-related, before a human teaches a mapping. | `services/learning/backend/app/keywords.py`, Learning queue UI | Deterministic vocabulary/pattern analysis, not a language model. The model in use is `qwen2.5:7b-instruct` (not "Coder"); it does extraction only, never compliance decisions. |
| PDFs customised to the device's model and software version | The PDF carries the device's model/version/serial and adds firmware-specific remediation notes where a rule matches the detected vendor and version (e.g. Cisco IOS 15.3+ scrypt secrets vs older releases). | `services/reporting/app/version_guidance.py`, `audit_report.html` | The rule table is small and operator-extensible; it changes remediation *advice* only. It does **not** change a control's severity or verdict, which stay with the OPA policy. Do not claim dynamic severity changes by firmware. |
| Clear Pass/Fail results with risk severity assessments | Every control is listed PASS or FAIL with its severity in the UI ("Risk Severity Assessments", "All controls" list) and in the PDF ("Pass / Fail Results and Risk Severity Assessment"). | `control_results()` in compliance and reporting, UI findings card | Eleven CIS-inspired demo controls; not a certification claim. |
| Rollback / disaster recovery for fixes | Every template fix ships with a rollback script (native `rollback 1` on Junos, reverse commands elsewhere); AI drafts carry a synthesized one. Shown in the UI and the PDF. | `services/remediation/templates/*.j2` (`@@ROLLBACK@@` section) | Rollback restores the pre-fix state, so it re-introduces the finding; lines marked REVIEW need original values from a pre-change backup. |
| Configuration drift tracking | Per-device history across audits: when a control started failing, what was introduced/resolved between audits; compare any two audits. | `services/compliance/app/drift.py`, drawer "Drift history", inventory "Compare two audits" | Devices are matched by vendor + hostname from the config. |
| Synchronised timestamps (CERT-In) | Internal NTP/Stratum 1 service config; every report states the measured clock offset against the time source. | `infra/ntp/`, `services/reporting/app/timesync.py`, `docs/TIME_SYNC.md` | Measures and reports drift; does not set the clock. A real Stratum 1 needs GPS/PPS hardware. |
| Physical isolation / data diode / USB kiosk | Documented transfer procedure for updates and configs, signed update bundles verified before install, and a landing-folder loader. | `docs/AIRGAP_UPDATE_PROCEDURE.md`, `tools/airgap_bundle.py`, `tools/ingest_dropbox.py` | The diode or kiosk is hardware/process, not software. |
| Parser sandboxing / anti-ReDoS / prompt injection | Line-length caps, injection-line neutralisation, bounded-time context detection, untrusted-data prompt framing, and a locked-down container (non-root, read-only, no capabilities, resource limits). | `services/parsing/app/input_guard.py`, `docs/PARSER_SANDBOX.md`, compose `parsing` | Heuristic injection patterns; seccomp/AppArmor/gVisor are documented options, not enabled by default. |
| Digital twin reachability (not just syntax) | Before a fix can be approved, the device's stored configuration is modeled and the script's ACLs are applied to it: routing sessions (BGP/OSPF/EIGRP) and SSH from protected management subnets are each marked PRESERVED or BROKEN. Any BROKEN blocks approval (RISK_FLAGS). | `services/remediation/app/twin.py`, drawer "Digital twin", PDF remediation plan, `docs/DIGITAL_TWIN.md` | Single-device model, Cisco-style ACL syntax only; other dialects report "not modeled", never safe. It is not Batfish and does not model other devices or routing convergence. Say "digital twin of the device", not "of the network". Batfish itself is still mocked in this build. |
| Cryptographically signed, tamper-evident ledger | Ledger events are sealed into Merkle trees; each root is Ed25519-signed and chained to the previous seal; verification detects edited, deleted or re-ordered history; any event has an inclusion proof an auditor can check offline. | `services/compliance/app/ledger_seal.py`, `merkle.py`, Reports → Ledger integrity, `tools/verify_ledger_proof.py`, `docs/LEDGER_INTEGRITY.md` | A signed hash chain, not a distributed blockchain. Protects events from the moment they are sealed; the key holder can re-sign; record the chain head outside the database. |
| Configuration drift "Time Machine" | For a failing control, the current baseline is diffed against the last audit where it passed; the fields that caused the failure are highlighted with the evidence lines. | `drift.py` (`baseline_diff`), drawer "What changed since it last passed?" | Diff is on the normalized baseline plus the control's evidence lines, not a raw text diff of the file. |
| Adversarial config detection is visible | Neutralised lines are recorded on the audit run and shown as a banner in the UI and a section in the PDF ("Adversarial content detected at the ingest gate"). | `input_guard.py`, `save_security_flags`, `audit_report.html` | Heuristic patterns; see `docs/PARSER_SANDBOX.md`. |
| Cyclical pattern detection on the compliance trend | The Executive report trend is a line chart; a discrete Fourier transform over the daily score history marks the low points of any recurring cycle with a warning triangle and tooltip. | `services/reporting/app/periodicity.py`, `TrendChart` | Needs 14+ days of history and a clear dominant period; otherwise the chart says no pattern was found. It is frequency analysis of the fleet score, not of individual devices' config changes. |
| Topological risk map / lateral-movement path | Routing topology from the graph database with each device coloured by its audit score; the weakest device is highlighted and the shortest routing path to the most-connected device is traced. | `services/compliance/app/risk_map.py`, Executive report "Blast radius topology" | Graph traversal, **not a GNN** — do not call it one. The path is a structural exposure route, not a prediction of attacker behaviour. Needs Neo4j and two or more audited, connected devices. |
| Multi-stage verification, not a single model | The audit screen's Verification pipeline shows four real stages with checkmarks only for checks that ran and passed: LLM extraction, independent deterministic cross-check, reverse-translation check, OPA policy verdict. | `VerificationPipeline` in `widgets.tsx` | These are checks inside one pipeline, not separate autonomous "agents"; there is no Critic or Remediation agent. |
| Deterministic verdict badge | "Deterministic verdict · OPA policy <version>" next to the score: every PASS/FAIL comes from version-controlled Rego. | audit header | The system uses OPA, **not Z3**; it does not claim formal proof. |
| Semantic comparison for unknown syntax | In the Learning queue, an unrecognised block is plotted against the mappings humans have already confirmed, with exact cosine similarity and the closest mapping named. | `services/learning/backend/app/similarity.py`, `SimilarityPlot` | Compares against confirmed mappings only (empty until the first one is taught). The 2-D view is a PCA projection; the similarity figures are exact. |
| Outage-risk figure | Not shown. The Digital Twin reports, per fix, which routing sessions and management paths are preserved or broken. | "Reachability simulation" under Generate safe fixes | There is no Monte Carlo simulation, so no probability is displayed. |
| Formal SMT verification (Z3) and CEGIS | ACL changes are encoded as bit-vector formulas; Z3 proves that every packet in each critical flow class (BGP/OSPF/EIGRP sessions, SSH from whole management subnets) stays permitted, or returns a concrete counterexample packet. A counterexample-guided loop synthesises the missing permit lines, re-proves the result, and refuses any repair that would admit traffic that must stay blocked. | `services/remediation/app/formal.py`, `twin.py`, drawer "Digital twin", PDF, `docs/DIGITAL_TWIN.md` | Proves facts about the parsed ACL model, not the whole network. Cisco-style ACL syntax only; other dialects report "not modeled". The compliance *verdict* is still OPA; Z3 verifies *fixes*. AI-drafted fixes are checked by the same solver; the model does not verify itself. |
| Frequency-domain drift analysis | FFT periodogram with Hann window and zero-padding, autocorrelation by zero-padded convolution (length >= 2N-1, so it is linear, not circular), and a permutation test; applied to the fleet score and to new violations per day. Recurring lows/peaks are marked and explained. | `services/reporting/app/spectral.py`, `periodicity.py`, Executive report | Needs about 3 weeks of history; measured false-alarm rate on random data is under 1%. It finds recurrence in fleet-level signals, not per-device insider activity. |
| Control-theoretic network model | The routing graph as a discrete-time boolean system x[k+1] = x[k] OR A^T x[k] from the weakest device; reports reach per step, hops to the core, and (by max-flow / Menger) the smallest set of links whose filtering isolates the core. | `services/compliance/app/control_model.py`, Executive report topology card | Models routing adjacency, not per-protocol ACLs or traffic volume; the state is reachability, not packet-level dynamics. |
| Exception / waiver management | An admin can waive one failing control on one device for a stated period. The waiver is a signed-ledger event with justification, approver and expiry; the finding is annotated, not hidden; it stops counting and alerting, then reverts automatically on expiry; the score is shown with and without waivers. | `services/compliance/app/waivers.py`, finding drawer, Reports register, PDF, `docs/WAIVERS.md` | Protected by the ledger seals only once a signing key is configured. The executive fleet score does not apply waivers yet. Needs migration 0013. |
